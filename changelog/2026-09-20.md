# ChangeLog 2026-09-20

In the rules, `E` is a CP expression and `e` is its elaboration. `Γ` contains
typing assumptions; `Ω`, where shown separately, contains module signatures.
Ambient type and disjointness contexts are suppressed. `⇒` means type
synthesis, `⇐` means checking against a given type, and `↝` means elaboration.
`⟦A⟧` translates a CP type to its Fiobs type. `A ∗ B` means disjointness;
`A ≃ B` means both `A <: B` and `B <: A`. Substitution is capture-avoiding.

## Primitive operands must synthesize their types

Previously an operator tried its available signatures by checking both operands
against each signature. Now CP first infers each operand's type, then chooses a
signature that accepts those types.

Before:

```text
op : p₁ × p₂ → p    Γ ⊢ E₁ ⇐ p₁ ↝ e₁    Γ ⊢ E₂ ⇐ p₂ ↝ e₂
────────────────────────────────────────────────────────── Primitive-before
Γ ⊢ E₁ op E₂ ⇒ p ↝ e₁ op e₂
```

Now:

```text
Γ ⊢ E₁ ⇒ A ↝ e₁    Γ ⊢ E₂ ⇒ B ↝ e₂
op : p₁ × p₂ → p    A <: p₁    B <: p₂
────────────────────────────────────────────────────────── Primitive-now
Γ ⊢ E₁ op E₂ ⇒ p ↝ e₁ op e₂
```

This is a typing change. For example, this used to be accepted:

```cp
def main = (if true then (41 ,, true) else 0) + 1;
```

Checking the conditional at `Int` accepts both branches. Inferring its type
instead starts with the first branch's `Int & Bool`, which the second branch
does not provide. Give the conditional its intended type explicitly:

```cp
def main = ((if true then (41 ,, true) else 0) : Int) + 1;
// 42
```

The reason for the change is that overload selection should use the operands'
types. It should not repeatedly elaborate an operand under different expected
types. Errors inside operands also survive: `missing + 1` reports the unknown
name instead of hiding it behind “no matching primitive signature.” Fiobs's
primitive checking rule itself is unchanged.

## Inferred definitions no longer get an extra whole-result cast

```cp
def payload = 42 ,, (1 / 0 == 0);
def main: Int = payload;
```

This now returns `42` on both backends. Previously Fiobs evaluation tried to
produce the whole `Int & Bool` result of `payload` and reached the division
by zero before the caller could select `Int`.

The extra demand came from checking an already elaborated definition against
its inferred type. Checking can insert a cast even when the types are equal.
The final judgment for an inferred definition now uses synthesis:

```text
Γ ⊢ E ⇒ A ↝ e    ⟦Γ⟧ ⊢ e ⇐ ⟦A⟧ ↝ r
────────────────────────────────────────── Definition-before
Γ ⊢ def x = E ↝ x : A = r

Γ ⊢ E ⇒ A ↝ e    ⟦Γ⟧ ⊢ e ⇒ ⟦A⟧ ↝ r
────────────────────────────────────────── Definition-now
Γ ⊢ def x = E ↝ x : A = r
```

Here the second premise is Fiobs typing and decoration, and `r` is the
executable term. Both backends use that same typing result.

A written annotation still has its meaning. Changing the first line to
`def payload: Int & Bool = 42 ,, (1 / 0 == 0);` explicitly requests both
components and still encounters the error.

## Local bindings substitute their values directly

Local `let` was already non-recursive and lazy. Those properties remain.
What changed is its elaboration: the body is no longer placed inside a
generated function whose result is cast to the body's entire inferred type.

```text
Γ ⊢ E₁ ⇒ A ↝ e₁    Γ, x : A ⊢ E₂ ⇒ B ↝ e₂
────────────────────────────────────────────────────────── Let-before
Γ ⊢ let x = E₁ in E₂ ⇒ B
  ↝ ((λx. e₂) : ⟦A⟧ → ⟦B⟧) e₁

Γ ⊢ E₁ ⇒ A ↝ e₁    Γ, x : A ⊢ E₂ ⇒ B ↝ e₂
────────────────────────────────────────────────────────── Let-now
Γ ⊢ let x = E₁ in E₂ ⇒ B ↝ e₂[x ↦ e₁]
```

For example:

```cp
def main: Int = let ignored = 0 in 42 ,, (1 / 0 == 0);
```

This now returns `42`. The old generated function imposed an `Int & Bool`
result cast and reached the error. Direct substitution removes that extra
cast; it does not change how an explicitly written function is checked.

An annotated binding substitutes `(e₁ : ⟦A⟧)` after checking its initializer
at `A`. A recursive binding substitutes a fixpoint:

```text
Γ, x : A ⊢ E₁ ⇐ A ↝ e₁    Γ, x : A ⊢ E₂ ⇒ B ↝ e₂
────────────────────────────────────────────────────────── LetRec-now
Γ ⊢ let rec x : A = E₁ in E₂ ⇒ B
  ↝ e₂[x ↦ fix(x : ⟦A⟧). e₁]
```

Previously the same fixpoint was passed to the generated function.
An ordinary `let x = E₁ in E₂` still does not bind `x` inside `E₁`.
For `open`, the corresponding substitution binds each field name to an
ascribed projection of the receiver. These changes retain call-by-name
evaluation; they do not promise that repeated uses share a computed value.

## Omitted inheritance is different from inheriting `top`

These are accepted:

```cp
def component = trait => { value = 42 };
```

```cp
def empty = trait => {};
def component = trait inherits empty => { value = 42 };
```

These are rejected:

```cp
def component = trait inherits top => { value = 42 };
```

```cp
def empty = top;
def component = trait inherits empty => { value = 42 };
```

Previously the literal `top` was treated as an omitted clause, although a
variable of type `Top` was rejected. Now every explicit parent must provide
a trait interface. The same requirement applies to `impl ... inherits ...`.

The distinction is algebraic: `top` is an empty provided value, whereas an
empty trait is a function producing an empty provided value.

```text
⟦Trait[A, B]⟧ = ⟦A⟧ → ⟦B⟧

A → ⊤ <: ⊤
⊤ ≮: A → ⊤
```

There is no TopLike conversion from `top` to an empty trait.

For the following rules, `F ▹ᵗ Trait[R,P]` means that `F` is built from
trait types, intersections, and exact `⊤`, and Fiobs arrow distribution gives
`⟦F⟧ ▹ₐ (⟦R⟧ → ⟦P⟧)`. The
[trait intersection section](#inheritance-and-composition-accept-intersections-of-trait-types)
gives the distribution rules.
`N(A)` removes exact-Top intersection units recursively; `N(A) ≃ A`.

The rule for an explicit parent is:

```text
Γ, self : A₁ ⊢ E₁ ⇒ F ↝ e₁    F ▹ᵗ Trait[A₂,B₂]    A₁ <: A₂
Γ, self : A₁, super : B₂ ⊢ open self in E₂ ⇒ C ↝ e₂
C ∗ B₂    C ∧ B₂ <: B₁    P = N(C ∧ B₂)
────────────────────────────────────────────────────────── Trait-Inherits
Γ ⊢ trait [self:A₁] implements B₁ inherits E₁ => E₂ ⇒ Trait[A₁,P]
  ↝ ((λself. e₂[super ↦ e₁ self] ,, e₁ self) : ⟦A₁⟧ → ⟦P⟧)
```

Previously omission used the following rule, which also treated a literal
`inherits top` as omission:

```text
Γ, self : A ⊢ open self in E ⇒ C ↝ e    C <: B
────────────────────────────────────────────────────────── Trait-Base-before
Γ ⊢ trait [self:A] implements B => E ⇒ Trait[A,C]
  ↝ ((λself. e) : ⟦A⟧ → ⟦C⟧)
```

Omission now binds a fresh `super`, whose value is `top`:

```text
Γ, self : A, super : ⊤ ⊢ open self in E ⇒ C ↝ e
C <: B    P = N(C ∧ ⊤)
────────────────────────────────────────────────────────── Trait-Base
Γ ⊢ trait [self:A] implements B => E ⇒ Trait[A,P]
  ↝ ((λself. e[super ↦ top] ,, top) : ⟦A⟧ → ⟦P⟧)
```

This uses `C ∗ ⊤` and `C ∧ ⊤ ≃ C`. It does not cast `top` to a function.

Previously an omitted clause introduced no local `super`, so a nested trait
could accidentally use an enclosing trait's parent. This is now rejected:

```cp
def parent = trait => { value = 42 };
def child = trait inherits parent => {
  nested = trait => { value = super.value }
};
def main = (new (new child).nested).value;
```

The nested trait has no parent. Its own `super` has type `Top`, which has no
`value` field.

## Inheritance and composition accept intersections of trait types

```cp
def left = { make = trait => { x = 20 } };
def right = { make = trait => { y = 22 } };
def both = left ,, right;
def child = trait inherits both.make => {};
def main = (new child).x + (new child).y;
// 42
```

The type of `both.make` is:

```text
Trait[⊤, {x:Int}] ∧ Trait[⊤, {y:Int}]
```

Previously `new` and forwarding already accepted this intersection, but
inheritance required a single `Trait[A,B]` constructor. Trait composition
also selected its special composition rule only for single trait types.
These operations now agree about which intersections provide a trait
interface. An exact-Top component is harmless on either side.

The reason is Fiobs's existing applicative distribution after trait
translation:

```text
──────────────────── AD-Arr
(A → B) ▹ₐ (A → B)

F₁ ▹ₐ (A₁ → B₁)    F₂ ▹ₐ (A₂ → B₂)
────────────────────────────────────── AD-And-Arr
F₁ ∧ F₂ ▹ₐ ((A₁ ∧ A₂) → (B₁ ∧ B₂))

────────── AD-Top
⊤ ▹ₐ ⊤

F₁ ▹ₐ ⊤    F₂ ▹ₐ ⊤
──────────────────── AD-And-Top
F₁ ∧ F₂ ▹ₐ ⊤

F₁ ▹ₐ (A → B)    F₂ ▹ₐ ⊤
────────────────────────── AD-And-Left
F₁ ∧ F₂ ▹ₐ (A → B)

F₁ ▹ₐ ⊤    F₂ ▹ₐ (A → B)
────────────────────────── AD-And-Right
F₁ ∧ F₂ ▹ₐ (A → B)
```

The result `⊤` of `AD-Top` supplies no arrow. Thus `traitValue ,, top`
retains a trait interface, but `top` alone does not acquire one.
Ordinary functions are still not CP traits.

When both merge operands provide trait interfaces, composition uses:

```text
Γ ⊢ Eᵢ ⇒ Fᵢ ↝ eᵢ    Fᵢ ▹ᵗ Trait[Aᵢ,Bᵢ]    B₁ ∗ B₂
────────────────────────────────────────────────────────── MergeTrait
Γ ⊢ E₁ ,, E₂ ⇒ Trait[A₁ ∧ A₂, B₁ ∧ B₂]
  ↝ ((λself. e₁ self ,, e₂ self) : ⟦A₁ ∧ A₂⟧ → ⟦B₁ ∧ B₂⟧)
```

The interfaces are taken modulo exact-Top units. Both traits still receive
the same `self`, and their provided interfaces must still be disjoint.

## Renaming a bound variable no longer changes typing

```cp
def keep[A](value: A) = Λ A . value;
def main: Int = keep[Int](42)[Bool];
// 42
```

The inner `A` does not change the type of the existing `value`. Previously
that shadowing could make `value` appear to have the inner type, so changing
the inner binder's name could change whether the program compiled.

The same correction applies to opened fields and local bindings carried
under later term or type binders. Type equality also respects alpha-equivalence:

```text
∀(A ∗ ⊤). A → A  ≡α  ∀(B ∗ ⊤). B → B
```

Here `≡α` means equality after consistently renaming bound variables.
For example, a parameter declared with the left type can be checked against
a function parameter expected to have the right type. This does not replace
equality with arbitrary mutual subtyping.

Substitution has not disappeared. It still obeys the usual capture-avoiding
laws, with fresh `C` and `z`:

```text
(∀B. A → B)[A ↦ B] =α ∀C. B → C
(λy. x)[x ↦ y]     =α λz. y
```

The free `B` and free `y` in the replacements must remain free. This is why
tracking the binder denoted by a reference matters more than its spelling.

## A universal binder does not scope over its own bound

```cp
type Signature<Sort> = { result: ∀ [type Sort * Sort] -> Int };
def value: Signature<Bool % Int> = { result = Λ (T * Int). 42 };
def main = value.result[Bool];
// 42
```

In `∀ [type Sort * Sort]`, the first `Sort` introduces the universal's
parameter. The second refers to the enclosing signature sort. The parameter
starts binding in the universal's body, after its disjointness bound.

The sort argument `Bool % Int` supplies `(Bool ∧ Int, Int)` as its negative
and positive types. At this position the bound uses the positive type, so
the expanded field type is `∀(T ∗ Int). Int`. Previously removing the sort
mapping too early left the bound as `Bool ∧ Int` and rejected the definition.

Write `Σ ⊢ A ↝ A′` for sort transformation at a fixed polarity and field
position. `Σ ∖ {α}` removes the sort mapping shadowed by the new binder.
The scope correction is:

```text
Σ ∖ {α} ⊢ A ↝ A′    Σ ∖ {α} ⊢ B ↝ B′
────────────────────────────────────────── All-before
Σ ⊢ ∀(α ∗ A). B ↝ ∀(α ∗ A′). B′

Σ ⊢ A ↝ A′          Σ ∖ {α} ⊢ B ↝ B′
────────────────────────────────────────── All-now
Σ ⊢ ∀(α ∗ A). B ↝ ∀(α ∗ A′). B′
```

The transformation's variance rules are unchanged. The correction is which
scope is used for the bound.

## Recursion follows resolved references and declared signatures

An opened field is a local binding, even when its name matches the surrounding
definition:

```cp
def record = { answer = 42 };
def answer = open record in answer;
def main = answer;
// 42
```

Previously the last `answer` could be counted as a recursive reference to
the module definition. Now it resolves to the opened field. The same applies
to fields implicitly opened from a trait's `self`.

The dependency criterion is:

```text
Ω ; Γ ⊢ E_g ⇒ A ↝ e_g    global h occurs in e_g
────────────────────────────────────────────── Dependency
definition g depends on definition h
```

Local variables and field projections do not create module dependencies.
Ordinary definitions and constructor methods now use the same criterion, so
forward references between them are accepted:

```cp
def main = (new Box(40)).eval;
(Box value: Int).eval = value + offset;
def offset = 2;
// 42
```

Qualified recursion also keeps its module identity under a local binder:

```cp
module Notes;
def f(n: Int): Int =
  if n == 0 then 42 else (λ(f: Int). Notes::f(n - 1))(0);
def main = f(2);
// 42
```

The parameter named `f` does not capture `Notes::f`. Previously recursion
elaboration could turn that qualified reference into the local name.

A genuine recursive definition still needs a declaration signature. An
expression annotation no longer doubles as that signature:

```cp
def f = ((λ(n: Int). if n == 0 then 42 else f(n - 1)) : Int -> Int);
// Rejected: f has no declaration signature.
```

Write the type on the declaration:

```cp
def f(n: Int): Int = if n == 0 then 42 else f(n - 1);
def main = f(2);
// 42
```

The distinction is that an expression annotation checks an expression in the
current environment; it does not declare a recursive name in that environment:

```text
Ω ; Γ ⊢ E ⇐ A ↝ e
────────────────────────────────────────── Annotation
Ω ; Γ ⊢ (E : A) ⇒ A ↝ (e : ⟦A⟧)

Ω, g : A ; Γ ⊢ E ⇐ A ↝ e    global g occurs in e
──────────────────────────────────────────────────── Declaration-Rec
Ω ; Γ ⊢ def g : A = E
  ↝ g : A = fix(x : ⟦A⟧). (e[global g ↦ x] : ⟦A⟧)
```

Every member of a mutually recursive group likewise needs a declaration
signature. The fixpoint semantics of recursion is unchanged.

## A type signature's name no longer blocks a term with the same name

```cp
type Signature<Sort> = { field: Sort };
def Signature[T](value: T) = value;
def main = Signature[Int](42);
// 42
```

Previously parsing rejected `Signature[Int]` just because a compositional
signature had that name. Now it is parsed as ordinary term-level type
application, and term lookup resolves the function. Local bindings work the
same way.

If only the type signature exists, using it as a term still fails. The error
now says that the name denotes a type where a term is required.
`Signature<Int>` remains signature instantiation in type syntax. This change
adds no Fiobs typing or evaluation rule.

## Duplicate bounds and duplicate sort parameters are rejected

```cp
def value[T * Top] where T * Bool = top;
// Rejected: two bounds were written for T.
```

Previously an explicit `Top` could be mistaken for an omitted bound and
replaced by the `where` clause. Other explicit bounds could silently win over
the `where` clause instead. There is now one rule: a binder may have at most
one written bound, wherever it is written. No written bound means the usual
default `Top`.

These remain equivalent:

```cp
def value[T] where T * Bool = top;
```

```cp
def value[T * Bool] = top;
```

Repeated sort parameters in one signature are also rejected:

```cp
type Pair<S, S> = { value: S };
```

This does not prohibit shadowing in nested scopes. These are declaration
well-formedness checks; bounds themselves keep their ordinary disjointness
meaning. In particular, `Bottom` is not a signal to bypass bound checking:

```text
Γ ⊢ E ⇒ ∀(α ∗ B). A ↝ e    C ∗ B
P = N(A[α ↦ C])
────────────────────────────────────────── Type-Application
Γ ⊢ E[C] ⇒ P ↝ (e[⟦C⟧] : ⟦P⟧)
```

## Exact-Top normalization does not add casts to ordinary merges

Types are normalized using the intersection unit law:

```text
A ∧ ⊤ ≃ A ≃ ⊤ ∧ A
```

Normalization recurses inside types, but preserves their constructors.
For example, `{value: Int & Top}` becomes `{value: Int}`, while
`Int -> Top` remains an arrow. This is not TopLike normalization.

An ordinary merge keeps the original rule, including its unsimplified
synthesized intersection:

```text
Γ ⊢ E₁ ⇒ A ↝ e₁    Γ ⊢ E₂ ⇒ B ↝ e₂    A ∗ B
────────────────────────────────────────────── Merge
Γ ⊢ E₁ ,, E₂ ⇒ A ∧ B ↝ e₁ ,, e₂
```

Thus `42 ,, top` synthesizes `Int & Top`. CP does not wrap each merge in an
annotation merely to normalize its type. Normalization is used when expanding
types and deriving interfaces, including after type substitution. Application,
type application, and forwarding ascribe their results to the resulting
interface; projection already needs an ascription to synthesize in Fiobs.
Trait introduction chooses a normalized provided interface at its existing
function annotation, as shown
in the [inheritance rules](#omitted-inheritance-is-different-from-inheriting-top).
That annotation is needed because a Fiobs lambda checks against
an arrow rather than synthesizing one by itself.

The distinction matters operationally:

```cp
def main: Int = 42 ,, (1 / 0 == 0);
// 42
```

Selecting the integer component need not evaluate the other component.
Adding a cast to the whole `Int & Bool` intersection would demand more work.
Mutual subtyping of types alone does not justify adding or removing such
casts. The changes to definitions and local bindings above remove accidental
casts; explicitly written annotations keep their semantics.
